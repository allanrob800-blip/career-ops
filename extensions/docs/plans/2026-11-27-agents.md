# Équipe d'agents de candidature — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Six spécialistes (agents Claude Code) préparent seuls les dossiers de candidature chaque matin. Le tableau de bord montre la stratégie de chaque dossier ; sur le Mac, « postule » remplit les formulaires et le candidat clique.

**Architecture:**
- **Couche fichiers.** Des fichiers JSON dans la couche utilisateur (`{DATA_ROOT}/data/dossiers.json`, `proposals.json`, `relances.json`, `output/*-strategie.json`). De petits scripts Node sous `extensions/agents/` les lisent, les valident et les écrivent.
- **Tableau de bord.** `extensions/dashboard/` les exporte dans l'instantané et accepte deux nouveaux types de demande (`why`, `retouche`).
- **Agents et routine.** Les agents sont des fichiers `.claude/agents/*.md`. La routine quotidienne et « postule » sont des procédures dans `modes/_custom.md` du candidat (tâche 8, faite par le contrôleur).

**Tech Stack:** Node 22 (`.mjs`, `node:test`), Playwright (bibliothèque, tests de page), claude.ai artifact (db, mcp, assets, **downloads**), sous-agents Claude Code.

**Spec:** `extensions/docs/specs/2026-11-27-agents-design.md` (à lire avec ce plan).

## Global Constraints

- Dépôt career-ops **public** : aucune donnée personnelle dans le code, les tests, les fixtures, les définitions d'agents ou les messages de commit. Les fixtures utilisent la candidate fictive « Camille Test ».
- Approche A : ne modifier aucun fichier système de career-ops. Les ajouts vont dans `extensions/` et `.claude/agents/`.
- Les scripts résolvent la racine des données par `path-resolver.mjs` (`getCareerOpsRoot()`), jamais par `__dirname`. Tout test qui lance un script fixe `CAREER_OPS_ROOT` sur un dossier de fixtures ou un dossier temporaire.
- Seul `set-status.mjs` écrit un statut. Les nouveaux types de demande n'écrivent que dans `data/dossiers.json`.
- Commande de test : `node --test 'extensions/dashboard/test/**/*.test.mjs' 'extensions/agents/test/**/*.test.mjs'`. Les 165 tests existants doivent rester verts.
- Playwright : `executablePath: '/opt/pw-browsers/chromium'` dans les tests ; jamais `playwright install` dans le cloud.
- Interface en français.
- Textes saisis sur la page (`why`, `retouche`) : espaces multiples réduits à un, 500 caractères au plus, aucun caractère de contrôle.
- Tout texte venant des fichiers ou de la base est échappé avec `CapUI.esc`, et toute URL `/_blob/` passe par `CapUI.blobHref`.
- Seuils : préparation si note **≥ 4,0** ; **au plus 3** dossiers préparés et **8** offres évaluées par jour ; légitimité « Suspicious » exclue.
- Interdits absolus : aucun envoi de candidature ou d'e-mail ; aucune écriture dans Outlook ; aucune connexion à un compte du candidat.
- Les sous-agents d'implémentation ne lancent jamais `git checkout/switch/reset/stash/rebase`.

## Review Focus

1. **Proposition périmée.** Le statut de la candidature a déjà changé, ou vaut déjà `to_status`. La proposition ne doit pas s'afficher (test dans la tâche 6).
2. **Texte hostile ou trop long.** Saut de ligne, `<img onerror>` ou plus de 500 caractères dans « pourquoi » ou « retouche » : texte normalisé côté page, refusé proprement côté script, toujours affiché échappé (tests dans les tâches 3 et 5).
3. **Fiche stratégie malformée ou trop grosse** écrite par un agent : les champs invalides sont écartés à l'export, sans plantage (test dans la tâche 4).
4. **Téléchargement indisponible.** `downloads` vaut `null`, ou la sauvegarde est refusée (`declined`, `rate_limited`, `host_unavailable`) : un bouton caché ou un message clair, jamais d'erreur non rattrapée (test dans la tâche 5).
5. **Dossier pour une candidature disparue du tracker**, ou numéro inconnu dans une demande : une demande rejetée avec une raison, et un instantané qui ignore l'entrée (tests dans les tâches 3 et 4).

## Contrats de fichiers (couche utilisateur)

`data/dossiers.json`. Un état `a_verifier` est mis par l'Expert après deux échecs du contrôle :

```json
{ "schema": 1, "dossiers": { "<num tracker>": {
  "state": "pret" | "a_verifier" | "a_refaire",
  "prepared_at": "ISO", "report_num": 3,
  "cv": { "pdf": "output/…pdf", "html": "output/…html" },
  "letter": { "state": "a_completer" | "prete", "why": "texte|null", "why_at": "ISO|null", "pdf": "output/…pdf|null" },
  "message": "≤ 1200 caractères",
  "answers": [ { "q": "…", "a": "…" } ],
  "strategy": "output/003-…-strategie.json",
  "check": { "ok": true, "reasons": [] },
  "retouches": [ { "text": "…", "at": "ISO", "done_at": "ISO|null" } ]
} } }
```

`output/{num}-{entreprise}-strategie.json` reprend les champs de la spec, § 6.3 :
- `titre_cv`, `angle`, `lettre_angle` ;
- `preuves` : `[{texte, source}]` ;
- `mots_cles_repris` : `[string]` ;
- `mots_cles_ecartes` : `[{mot, raison}]` ;
- `ecarts` : `[{exigence, traitement}]` ;
- `verification` : `{ok, reasons}`.

`data/proposals.json` : `{schema:1, generated_at, items:[{id, ref, to_status, evidence:{from, date, subject, excerpt}}]}`. L'`id` vaut `"p-"` suivi des 16 premiers hexadécimaux de `sha1(message_id + to_status)`.

`data/relances.json` : `{schema:1, items:{"<num>": {text, generated_at}}}`.

`data/dashboard.json` → `cv_assets[num]` gagne `letter_asset_id`, `letter_file`, `letter_sha256` et `letter_pages`, sur le même modèle que le CV.
